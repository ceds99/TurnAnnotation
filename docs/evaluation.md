# 反馈组装的多维评测与非劣效实验

状态：实验协议草案，未运行。只覆盖固定修改意图的模型/产物评测。数值验收边界、样本量及模型版本均未最终锁定。

## 研究问题

在相同会话起点、修改意图、宿主配置与执行环境下，TurnMargin 的反馈组装能否保持回答与产物质量，并将整个任务的 token 开销控制在预先接受的范围内？

把“回复到了”和“实际做好了”分开测量。模型说“已完成”不是成功证据。

## 复用工具而不是重建通用平台

已确认初版方案：**Promptfoo + TurnMargin 专用评分/统计代码 + 原生适配校验**。具体运行适配、统计界值和正式样本量尚未验证/锁定。

| 工具 | 可复用能力 | 仍需本项目完成 |
| --- | --- | --- |
| [Promptfoo assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/) | 确定性断言、自定义 JS/Python、模型评分、成本和延迟检查 | 请求拆分、真实产物评分、配对设计、非劣效判定 |
| [Promptfoo custom provider](https://www.promptfoo.dev/docs/providers/custom-api/) | 接入宿主并返回 output、tokenUsage、cost、metadata | 将宿主原始用量映射为明确不重叠的指标 |
| [Claude Agent SDK provider](https://www.promptfoo.dev/docs/providers/claude-agent-sdk/) | agent 执行与配置入口 | 与原生 CC 的 system prompt、工具、项目指令和会话状态一致性验证 |
| [Codex app-server provider](https://www.promptfoo.dev/docs/providers/openai-codex-app-server/) | 会话/turn 元数据、流式事件汇总、用量 | 不接管当前 Desktop 会话；独立进程评测结论仍需原生接入验证 |
| [Inspect AI](https://inspect.aisi.org.uk/scoring.html) | 自定义 scorer、多维评分、分组统计；支持 sandbox 产物检查 | 可作为更复杂 agent 实验的备选，不同时维护两个平台 |

Promptfoo 的 Codex provider 明确区分 token 与估计费用，且费用可能缺少缓存写入或特定服务档位信息。SDK/provider 可运行不代表精确复现原生客户端。不能用一次裸模型 API 实验声称完整 harness 已验证。

框架负责运行和记录；高置信结论来自实验设计、样本与评分正确性，而不是安装某个工具。

## 三组反馈

- **A：普通编号/bullet 反馈**。忠实表达相同修改意图，不能故意写差。
- **B：高质量手工短引用＋要求**。主对照，包含足以定位的上下文。
- **C：TurnMargin 组装**。使用与 A/B 相同的原文、批注正文和自由输入。

引用长度和组织方式是被研究的因素；底层需求信息保持相同。不得给 C 更多隐藏需求、专属项目规则或更高权限。

若 B/C 的最终模型输入完全一致，视为组装可靠性的校验点，不能将随机输出差异归因于 UI。

## 两个验证层次

1. **组装器契约校验**：无需模型，验证零批注透传、正文保真、选区对应、重复引用、代码/Unicode、多条批注、自由输入、顺序、无历史重发、无额外模型请求。
2. **固定任务的 agent 实验**：从相同 fixture/会话起点运行 A/B/C，依据实际结果评分。集成试验额外检查最终进入原生会话的角色与内容。

第一层通过不代表第二层质量非劣效；第二层通过也不自动证明 UI 便利。

## 指标定义

先为每个案例编写独立的原子请求清单，并定义每项的判定标准。补充输入中的无关问题同样进入分母。

| 指标 | 定义 | 注意事项 |
| --- | --- | --- |
| 请求覆盖率 | 有实质回答或处理的请求数 / 全部请求数 | 仅复述、承诺“会处理”不计；可将澄清单独标记 |
| 请求落实率 | 验收断言通过的请求数 / 全部适用请求数 | 核心指标；必须有产物或答案证据 |
| 全部请求成功率 | 所有必需请求通过的案例数 / 全部案例数 | 反映“最后一个要求被遗漏”的问题 |
| 定位错误率 | 修改错误对象的请求数 / 可判定定位的请求数 | 重复短语、跨段引用是重点 |
| 回归率 | 被新修改破坏的既有约束数 / 需保持的既有约束数 | 不能靠删掉旧要求换取新要求通过 |
| 格式有效率 | 满足 JSON/schema/表格/文件等格式要求的案例比例 | 格式正确不代表内容正确 |
| 输出有效性 | 依据任务测试、精确值、结构或人工 rubric 得分 | 不使用文本长度或礼貌度替代质量 |
| token 用量 | 新增输入与完整任务实际模型调用用量，分别报告 | 缓存/推理字段依供应商语义拆分，避免重复相加 |
| 费用 | 实际记录或明确标记的估计值 | 缺失为 null；不能当作 0；订阅额度不是 API 美元费用 |
| 请求/工具次数与延迟 | 全部模型请求、工具调用、墙钟时间 | 包含重试，区分环境失败与 agent 失败 |

逐案例计算覆盖/落实比例后取宏平均；同时报告微平均，但不能让需求很多的少数案例支配结论。分母为 0 的指标为不适用，不能填 100%。

“澄清”只有在该案例的预设目标本身要求澄清时才算落实；对信息完整的任务提出无必要澄清不能替代完成。

## 产物评分优先

- JSON：解析、schema、精确字段、数值和额外字段检查。
- 代码：在隔离环境运行预先编写的行为测试，并检查需保持的接口/约束。
- 文档：章节、指定事实、必含/禁含内容及人工校准的 rubric。
- 开放回答：盲评；模型 judge 作为辅助，固定 judge 版本并用人工样本校准。

评分必须由任务意图导出，不能照抄组装器输出结构。避免仅检查“SQLite”这样的关键词：模型可能在解释为何不使用它。

## 用量口径

保留每个实际模型请求的原始 usage 与来源，随后按适配器版本转换：输入、缓存读取/写入（若可获取）、输出、推理（若已包含于输出，不再次相加）。提供 canonical total 的明确计算方式。

分别报告：本次反馈文本 token、目标 turn 总用量、预设后续窗口的完整任务用量、评测 judge 开销。judge 成本属于实验预算，不混入产品运行成本。

原生自动压缩、内部重试若已计入请求日志，应计入总用量；取不到的字段明确标为未知。不能把 UI 本地存档大小算入 token，也不能忽略已发送消息在后续上下文中的正常成本。

首个实验固定为一个反馈 turn；后续多轮实验必须预先固定修复策略、停止条件和最大轮数，不能只给某一组额外人工补救。分别报告成功率与成本，不只对成功任务计算成本。

## 配对设计与复现

- 每个任务族构造多个独立案例；A/B/C 从同一原文、代码树、会话历史及环境状态开始。
- 从原生会话分支进行配对时记录分支语义；无法重建相同历史时标记局限，不能假装只改了反馈格式。
- 冻结模型精确标识、harness/插件版本、推理设置、工具、权限、项目指令、工作目录 fixture、上下文压缩状态和输出预算。
- 随机交错运行组别，避免模型服务随时间变化造成偏差。
- 重复运行用于衡量随机性；同一任务多次运行不算多个独立任务。
- 实验缓存不能把前次模型输出作为新的独立采样；真实模型 prompt cache 则单独记录并平衡执行顺序。
- 测试集从开发案例中分离；调组装格式时不反复查看保留集结果。

## 非劣效判定

主比较预先固定为 C 对 B。设质量差值为 `D = quality(C) - quality(B)`，非劣效界值为 `delta_Q > 0`。

只有差值置信区间的下界 `L > -delta_Q`，才判质量非劣效。初步建议采用双侧 95% CI 的下界（对应单侧 2.5% 检验），最终应在正式实验前锁定。

token 采用预先定义的比率，如相同任务集合的算术平均总 token 比 `R = mean(T_C) / mean(T_B)`。只有比率上置信界低于 `1 + delta_T` 才通过开销门槛；是否证明节省则需上界低于 1。未知用量不能替换为 0。

在任务层面保留配对，通过任务簇 bootstrap 或适合数据类型的配对区间估计不确定性。同一模板衍生案例若相关，应提升聚类层级。稀有失败/很小样本时不能盲用正态近似或不稳定 bootstrap。

正式结论必须区分：通过、明确未通过、证据不足。`p > 0.05` 不能证明质量相同。宏平均质量、完整案例成功率和严重定位/回归错误应同时展示，不能用加权总分掩盖严重失败。

所有共同主门槛都通过才宣称总体通过；多个次要指标的改善主张需处理多重比较。模型或 harness 分开报告，不能凭合并结果声称每种环境均成立。

## 样本量与停止规则

先用 pilot 检查评分器、成本和任务分布，再按预先接受的质量/成本界值、配对差异和目标功效估算正式样本量。初步功效目标可为 80%–90%，最终取值需锁定。

尚未确认任何“2 个百分点”“5%”之类门槛。严格的小幅非劣效界值可能需要大量独立任务；预算不够时应缩小结论范围或报告证据不足，不能事后放宽界值来通过。

锁定样本数与停止条件。基础设施错误预先定义成对重跑/排除策略，保留全部审计记录；agent 自身失败和超时不能被静默删除。

## 运行记录建议

每条记录包括 case_id、task_family、arm、replicate_id、fixture/hash、组装器版本、宿主/模型配置、实际 user message、trajectory、产物校验、逐请求评分及证据、原始 usage、用量来源、延迟、错误类型。

真实运行存入忽略目录 `evals/runs/`，公开报告使用人工构造案例或经过检查的数据。当前 [示例案例](../evals/cases/structured-output.json) 仅示范任务与评分意图，不是跑过的 benchmark。
