# 架构与反馈组装契约

状态：产品边界已确认；数据模型、文本格式和具体宿主 API 是待验证的设计提案。

## 数据流

```text
原生回复的消息事件 / 选区接口
             ↓
批注 UI ───→ 本地批注与原文快照
   │
   └─ 本次选中的批注 + 正常输入框文字
                    ↓
           确定性的反馈组装器
                    ↓
             用户可见的发送预览
                    ↓
          原生输入提交路径的一条 user message
                    ↓
           原有 harness / 模型 / 工具循环
```

## 1. 批注界面

优先使用宿主支持的消息与 UI 扩展接口，UI 本身不调用模型。

用户编辑批注时可更新本地组装预览；尚未完成的批注不自动发送。发送应由用户最终动作触发。输入框中的自由文本、附件和宿主已有功能不能因批注而丢失。

选区接口若不能可靠返回目标消息和文本范围，不应通过截图/OCR、屏幕坐标或私有 DOM 抓取补齐。需要记录能力缺口，评估宿主原生组件或经用户接受的降级。

## 2. 本地批注记录

建议字段：会话引用、消息引用、原文快照引用、选区文字、前后文、范围、批注正文、创建/编辑时间、本次发送引用、组装器版本、实际提交文本。

字段只服务于 UI、存档和复现。内部 ID 不能冒充模型可理解的引用。

优先使用宿主稳定消息 ID 和不可变的原文快照；位置坐标必须定义为原始文本中的字符范围，不能是屏幕行号。范围仅作辅助，验证时必须与选中文字一致。重复语句通过消息、位置及前后文区分。

原生选择形式尚未确定，因此第一版不提前实现复杂“动态重锚定”。旧消息被重生成、分支或不可访问时，保留批注所对应的旧快照。不能悄悄转移到相似句子。

## 3. 反馈组装

建议接口：`assemble(batch, freeform) -> { userText, localManifest }`。

`userText` 是唯一发送的普通用户文字；`localManifest` 保存批注与输出段落的映射，不发送。

### 不变量

1. 没有批注时，自由文本原样通过，不增添模板前后缀。
2. 本次每条批注都可在输出中定位；不遗漏、不合并改写。
3. 用户正文和补充输入保留内容、代码及必要格式，不进行语义润色。
4. 引用明确标记为原文；不将 agent 的原话转换为用户的新要求。
5. 只加入本次所需的原文，不重复复制整篇回复；必要长引用不得为达成预算而静默截断。
6. 不加入历史批注、隐藏提醒、解决状态、时间戳或冗长说明。
7. 原有附件及其他输入块由适配层保留，不将整个宿主输入强行降成纯文本。
8. 同一输入和同一组装器版本产生相同文本，组装过程为零模型调用。
9. 本地预览与实际交付宿主的组装文字一致；其他宿主插件可能继续改写时必须在集成验证中检测。

### 文本格式候选

第一版比较短引用与最小结构化编号，不预先认定 JSON/XML 比普通文字更好。示例见 [feedback.txt](../examples/feedback.txt)。

多条批注针对同一段落时，可以共享一次原文引用，但各批注正文应保持分离、顺序可预期；这一优化也要进入实验。

### 提交语义

选中的批注在用户发送时冻结为一个 batch，并与自由输入组装。沿用宿主正在运行、排队、取消和失败的行为，不自行抢占 agent。

适配层必须知道自己的重试是否会产生第二条消息。在无法确认投递时保留草稿及明确状态，不自动盲目重发。宿主接受提交后保存实际发送文本；此后普通输入不再附带这批批注。

“自动包装”是本地确定性文本编辑；不代表自动发送、代理模型 API 或额外运行一个 agent。
