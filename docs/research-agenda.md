# 可交付的研究与工程工作

状态：2026-10-09 工作建议。Claude Code Mods 与 Promptfoo 路线已获用户同意；本页的交互细节与实验变体尚待实现和检验。

## 定位

Plannotator 已覆盖最后一条回复批注与回传，Herdr Annotate 已覆盖终端中的回复批注。因此不以“可以批注 agent 回复”本身作为独有贡献。[Plannotator](https://github.com/backnotprop/plannotator)、[Herdr Annotate](https://github.com/plannotator/herdr-annotate)

项目可以交付一个范围较窄的原生实现，以及独立可用的组装核心、案例和评测方法。即使某项功能已被其他项目实现，可信的对照结果、明确失败条件和可复用组件仍有价值。当前没有证据证明现有工具缺少相应能力或评测。

## 交付一：原生对话的一次提交

最小纵向流程：在 Claude Code 回复中批注两处，在正常输入框加入一个无关问题，查看最终文本，一次发送，之后回看记录。

重点验证宿主原生选区和输入组合，而不把“有一个侧栏”作为完成。CLI 与 Desktop Code tab 分别记录支持范围，不以浏览器窗口或第三方终端替代原生实现后仍称其为相同交互。

验收证据：用户交互录像/手工复现步骤、宿主版本、普通 user message 的角色和内容、本次请求次数、下一轮不重复带入、重启后的历史恢复。录像仅为测试证据，不是产品获取选区的手段。

## 交付二：独立的反馈组装核心

输入固定为来源文字、本次批注与自由输入；输出为普通用户文本和仅本地可见的映射。与宿主、模型和存储解耦，便于其他项目采用，也便于将既有工具的格式接入相同基准。

保留批注原文，不用模型润色。首版只研究少量明确变体：

| 变体因素 | 对照 | 问题 |
| --- | --- | --- |
| 引用范围 | 选区 / 选区加必要邻文 / 完整段落 | 哪些任务需要额外上下文，代价是多少？ |
| 表达形式 | 简单编号 / 短引用加要求 | 更明确的对应关系是否改善落实率？ |
| 重复引用 | 每条重复 / 相同来源共享一次 | 去重是否省 token，是否引入歧义？ |
| 批注排列 | 创建顺序 / 原文顺序 | 是否影响遗漏，尤其是补充问题？ |

不一次遍历所有组合。先测引用范围和一种简单格式，冻结候选后再在保留任务上确认。更短并非天然更好；看质量与开销的共同结果。

## 交付三：可复用的反馈落实基准

公开人工构造的原文、用户意图、多个反馈表示、输出验收和运行协议。基准允许替换组装器，既可测本项目，也可测人工反馈及现有工具。

优先覆盖以下失败类型：

- 多段出现相同短语，修改应落在指定对象。
- 选择“这个方案”等缺乏独立语义的片段。
- 一个批注包含多个原子要求。
- 多个批注修改同一对象，不能丢失其中一项。
- 多条批注之外还有一个无关问题。
- 删除、否定和“保持不变”的约束。
- 代码、表格、JSON 或有精确格式要求的输出。
- 中英文和 Unicode 选区。
- 用户引用的原文含有指令式语句，不能误当成新要求。
- 既有需求不应被本次修改破坏。

这些是任务类别，不是十个案例就足以得出高置信结论。开发集、pilot 和保留集分离；重复采样不冒充独立任务。

## 交付四：原生消息一致性检查与实验报告

在本地实验中建立 `批注输入 → 发送预览 → 宿主接受的 user message → 输出/产物 → 评分` 的记录链。仅采集测试所需内容，不给产品增加遥测，不代理加密模型请求。

原生可获取的消息记录不一定等于服务器最终接收的完整 prompt，应准确标注观察边界。无法验证的步骤标为未知，不能用 UI 文本推断完整模型输入。

至少包含两个控制条件：

1. 零批注时，用户输入原样通过，插件不发起模型调用。
2. 手工与工具产生完全相同用户文本时，不将模型随机差异解释为 UI 效果。

用 [评测协议](evaluation.md) 报告落实率、严重错误、token 和置信区间。支持“未通过”和“证据不足”的结论，保留失败案例。

## 建议优先级

先完成原生能力 spike 和最小组装核心，再建立少量带确定性验收的开发案例；随后打通真实流程，开展 pilot 和正式实验。暂不扩展多平台、云同步、AI 辅助评论、协作和多种富媒体。

如果同类实现已充分满足原生体验，可把精力转向组装核心、基准和上游贡献；如果实验显示高质量手工格式已足够，则采用这种简单格式，不人为增加结构。
